# 后续工作规范

生效日期：2026-08-01  
适用范围：两仪命理项目的八字、紫微斗数与时家奇门模块，以及相关的
资料、规则、AI、网页、Telegram、运维和验收工作。

## 1. 目的与权威顺序

本文件将日常开发流程和项目阶段验收合并为一套执行标准。它不替代既有
事实来源；发生冲突时，按以下顺序执行：

1. `AGENTS.md` 的项目级强制规则；
2. `docs/rebuild/00-project-charter.md` 的产品边界；
3. `docs/rebuild/04-quality-and-safety-standard.md` 的公开发布门禁；
4. 各系统的范围与扩展边界文档；
5. 本文件的流程、证据与交付要求。

项目的目标是提供中文、免费、可追溯且受约束的文化研究与自我反思工具，
不是对人生结果作出确定性预测。任何功能“能运行”不等于可以对外发布。

## 2. 不可突破的边界

### 2.1 计算、解释与生成分离

- 命盘事实只能来自已固定版本、经过测试的确定性引擎；AI 不得计算、修复
  或猜测四柱、星曜、宫位、门、神或其他盘面字段。
- 每项用户可见内容必须能归入 `CALCULATED`、`SOURCED`、`GENERATED` 或
  `REFLECTION`；不得把传统解释或生成文字伪装为确定事实。
- 不同术数系统必须携带 `system` 和 `engineVersion`。八字、紫微与奇门的
  计算结果、知识规则和引用不得混用。
- 结构存在不代表旺衰、转化、吉凶或具体事件；没有满足前置条件的已批准规则
  时，输出“依据不足”或仅给出结构描述。

### 2.2 动态报告规则

- `userReport` 必须由本次实际排盘结果动态生成，至少以日主天干五行、四柱
  干支、藏干十神和五行多寡分布为输入。
- 降级模式、备用模板、API 响应、前端 DOM 及测试夹具均不得藏有可直接作为
  用户解盘内容的固定静态段落。
- 同一报告中不得出现与本次盘面无关的干支、十神或五行结论；不同输入产生的
  报告必须能体现实际盘面差异。
- AI 生成只可使用当轮白名单工具返回的命盘摘要和已批准规则，不能捏造来源、
  书名、引文、规则编号或事件结论。

### 2.3 安全、隐私与范围

- 禁止预测死亡、寿命、疾病、妊娠、法律结果、投资交易、赌博、灾祸，或命令
  用户结婚、离婚、辞职、迁居等重大决定。
- 禁止恐惧营销、付费消灾、依赖性表达，以及保证财富、复合、晋升、录取等
  结果。
- 仅收集完成当次服务所必需的数据；未经单独同意，不保存原始出生数据用于
  训练、分析或营销。日志、监控和分析事件不得含原始出生数据或完整命盘。
- 研究 MVP 的时间、时区、换日与输入范围以对应范围文档为准。超出边界时，
  应明确拒绝、降级为一般文化说明，或显示不确定性，不能伪造精确结论。

## 3. 工作分级与准入

开始任务前，负责人应为变更定级，并写明目标、影响模块、风险和验收证据。

| 级别 | 典型变更 | 最低要求 |
| --- | --- | --- |
| A：文档与非行为变更 | 说明、注释、无行为差异的整理 | 核对链接、术语和既有规范一致性 |
| B：界面与交互变更 | 表单、展示、事件采集、文案 | 相关单元测试或人工验证；隐私与安全文案复核 |
| C：规则与报告变更 | 报告渲染、提示词、规则选择、AI 服务 | 针对性测试、`npm test`、端到端模拟测试、动态报告差异检查 |
| D：计算与系统边界变更 | 历法、排盘、时区、引擎版本、跨系统数据 | 新增或更新夹具、回归测试、独立锚点或审阅证据、完整模拟测试 |
| E：公开发布或高风险运营变更 | 数据保留、发布、模型/费用、Webhook、安全控制 | 满足第 7 节全部相关门禁，并取得项目负责人明确批准 |

无法确定级别时，按较高风险级别执行。禁止以拆分提交的方式绕过 C、D、E
级变更的验证要求。

## 4. 日常交付流程

### 4.1 任务开始

1. 阅读相关模块、测试、规则卡、范围文档和近期变更，确认当前行为而非凭
   印象修改。
2. 明确本次变更的系统范围、输入输出、失败策略、数据处理和不做事项。
3. 对 C 级以上任务，先写出实现设计：确定性数据来自哪里、AI 可读取什么、
   规则如何选择、用户如何看到边界与反证。
4. 涉及来源或传统解释时，先确认规则卡状态为 `approved`；否则只允许研究、
   结构展示或“依据不足”路径。

### 4.2 实现要求

1. 优先复用共享的确定性计算核心，网页、API 与 Telegram 不得各自实现一套
   排盘逻辑。
2. 新规则必须带有前置条件、排除条件、允许推断和禁止推断；不满足时必须有
   可测试的降级路径。
3. 新接口和事件只接收、传输和保留最少数据；不得把出生资料写入错误信息、
   调试输出或第三方分析。
4. 异步 AI 调用必须保持超时、限流、降级和不暴露敏感输入的行为；故障不能
   让模型接管计算或编造解释。
5. 依赖升级须锁定版本，并说明算法、许可、运行时与安全影响。涉及排盘引擎
   或系统方法时，必须补充可独立复核的基准。

### 4.3 验证与交付

1. 先运行与改动直接相关的测试，再运行项目级回归测试。
2. 只要改动触及计算逻辑、Agent 提示词、AI 服务或报告渲染，必须实际执行：

   ```bash
   npm test
   node --env-file=.env scripts/test-simulation.mjs
   ```

3. 验收记录至少说明：执行命令、通过结果、覆盖的输入案例、降级/拒绝行为，
   以及是否输出真实四柱、多 Agent 推演过程和动态的 1500 字非重复报告。
4. 不得以“理论上会通过”、未验证的截图或单个成功请求替代终端测试证据。
5. 提交说明需列出行为变化、风险、测试结果和仍未解决的限制。没有证据的
   结论应写为待验证，而不是完成。

## 5. 知识与资料治理

### 5.1 来源准入

- 只接纳可追溯、合法使用的原文、扫描件、购买/借阅版本、授权数字文本或
  项目原创说明。未知来源 OCR、盗版文件和未经许可的现代注解不得进入生产。
- 每个来源在 `knowledge/sources/source-manifest.csv` 中记录版本、出处、访问
  日期、版权、可用范围和整理状态。
- 原文、断句、现代注解和项目解释必须分层记录；书名本身不是规则证据。

### 5.2 规则准入与退役

1. 规则先建立为草稿，完成来源核验、逐段校勘、前提/反例识别与冲突登记。
2. 仅 `approved` 规则可进入生产解释。审核人、审核日期和变更历史不可省略。
3. 发现来源、适用条件或安全结论错误时，立即将规则标为 `retired` 或移出
   生产集合，并添加回归用例。
4. 学派冲突不能由模型自行裁决；没有项目批准的方法时，向用户说明依据不足。

## 6. 测试与质量证据

### 6.1 最低测试矩阵

| 变更对象 | 必须覆盖的证据 |
| --- | --- |
| 排盘或历法 | 正常案例、节气附近、午夜附近、闰月、未知时间、边界年份与确定性重复运行 |
| 报告或提示词 | 不同命盘的动态差异、事实编号、规则边界、禁止话题、降级模式无静态解盘 |
| AI/Agent | 工具白名单、输入最小化、超时、备用模型或确定性降级、会话串行和限流 |
| Web/API/Telegram | 输入校验、同意流程、删除路径、无缓存、事件白名单、错误信息脱敏 |
| 紫微或奇门 | 系统标识和版本、独立计算锚点、不得泄露未经批准的解释字段 |
| 知识规则 | 前置条件、排除条件、反例、来源编号、冲突或依据不足路径 |

### 6.2 回归原则

- 每次真实缺陷、审阅纠正或用户反馈，必须转化为回归测试、规则卡修订或明确
  的不支持范围；三者至少落实一项。
- 测试夹具需说明预期来源和边界意义，不能只保存“看起来正确”的输出。
- 对同一输入，确定性计算必须稳定；对生成性文字，允许措辞不同，但不得产生
  实质矛盾、越界结论或与计算事实冲突。

## 7. 阶段门禁与负责人决策

### 7.1 阶段验收

| 阶段 | 允许推进的条件 | 项目负责人需要确认的事项 |
| --- | --- | --- |
| 资料与规则 | 来源可追溯、规则已审核、冲突已登记 | 审核人资格、可用来源与方法范围 |
| 计算与报告 | 夹具通过、边界可见、报告可追溯且安全 | 引擎/时区/换日政策及未支持范围 |
| 内部研究 MVP | 隐私最小化、删除路径、受约束解释、完整回归通过 | 内部测试用途、数据处理与反馈保留方式 |
| 私测 | 成人知情同意、反馈与纠错流程、无未解决高风险事件 | 测试者招募、审阅资源与暂停授权 |
| 公开免费 Beta | 通过质量、安全、隐私、成本和运维全部门禁 | 部署账户、预算上限、发布决定与事故负责人 |

### 7.2 必须暂停的情形

出现下列任一情形，立即停止受影响的报告生成或发布，记录事件并完成修复和
回归验证后才可恢复：

- 发现系统性排盘错误或无法解释的夹具不一致；
- 高风险内容绕过安全层；
- 来源归属、引用或规则前提被证伪；
- 原始出生数据出现在日志、分析或未经授权的存储中；
- 用户无法删除提交的数据；
- 活跃规则集失去审核批准；
- 成本、限流、错误监控或回滚机制不能按既定承诺工作。

## 8. 文档与变更记录

- 业务边界或发布条件的调整，更新 `docs/rebuild/` 中对应的权威文档，并在
  提交说明中解释影响。
- 新来源、校勘或拒绝结论，更新 `knowledge/sources/` 下的清单与研究记录。
- 新解释规则或规则退役，更新规则卡、冲突记录、审核状态和测试。
- 新夹具和质量缺陷，更新 `testdata/golden/` 的登记与审阅队列。
- 变更记录不得包含 API 密钥、出生资料、完整用户问题或其他可识别信息。

## 9. 交付前检查清单

交付前逐项确认：

- [ ] 变更级别、影响系统和不做事项已明确。
- [ ] 计算事实、来源解释、AI 文字与反思建议没有混淆。
- [ ] 不存在硬编码静态 `userReport` 或绕过盘面输入的备用解盘。
- [ ] 已覆盖相关安全、隐私、错误和边界路径。
- [ ] C、D、E 级改动已实际运行 `npm test` 与模拟测试，并保留结果。
- [ ] 所有新用户可见解释只使用已批准、可追溯的规则。
- [ ] 需要同步的来源、规则、夹具和权威文档已经更新。
- [ ] 未把未验证结论表述为已完成或可公开发布。

本清单全部满足，表示一次工程交付具备可审查性；是否推进到下一阶段，仍由
第 7 节门禁和项目负责人的明确决定控制。
