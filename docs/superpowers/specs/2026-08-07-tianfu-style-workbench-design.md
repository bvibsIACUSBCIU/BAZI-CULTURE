# Tianfu 风格命理工作台设计

## 目标

将两仪从单页命理展示改造成以命主为中心的专业推演工作台：用户先选择命主，再得到完全确定的八字、紫微、奇门数据，并以可追溯的多 Agent 对话获得专题化分析报告。体验参考 Tianfu 的三栏工作流与分步推理展示，但不复制其账户、支付、积分或私有接口。

## 保留的产品约束

- 八字、紫微、奇门排盘只能由本地确定性引擎计算；AI 不得补造盘面事实。
- `userReport` 必须从实际四柱、日主、十神、藏干、五行、关系与提问专题动态生成；代码、降级路径和 DOM 中均不得保留静态解盘段落。
- 每轮对话展示任务规划、事实取数、专题分析、报告写作、摘要和追问六个可核对阶段。
- 命主、会话和收藏应以已签名的钱包账户为边界持久化；未连接钱包时不得伪造账户或命主。
- 新版测试体系必须有至少 87 个有效断言，模拟脚本必须输出真实四柱、完整 Pipeline 和足量且不重复的动态解盘报告。

## 交互与信息架构

### 左栏：持续上下文

左栏承载新建对话、命主档案、收藏会话和历史会话。选择或创建命主后，工作台同步请求三个确定性排盘端点；无钱包或无档案时使用明确的引导状态，而非自动创建虚构档案。

### 中栏：专题化推演

中栏是当前命主的对话主线。输入问题后，SSE 依次渲染六阶段状态和每一专题组的事实依据；最终显示简要对话回答、完整 Markdown 报告、可复制的长报告和 1–3 个推荐追问。报告正文随专题改变：事业、财富、关系、健康、总览不会互相套用固定段落。

### 右栏：可复查的命盘证据

右栏固定呈现紫微盘、八字四柱/十神/五行和奇门结果。所有数值和干支均直接来自 API 返回的确定性 chart；报告中的事实引用应能回到该证据层。

## 数据流

```text
已签名钱包 → 命主档案 → 并行确定排盘
                           ↓
用户问题 → 任务规划 → 确定性事实取数 → 专题 Agent 分析
         → 报告撰写 → 摘要与追问 → 会话持久化
```

`api/report.js`、`api/ziwei.js` 与 `api/qimen.js` 是命盘事实源。`api/chat.js`/`api/ai-report.js` 调用六阶段 Pipeline。前端只消费这些 API 结果；任何网络失败都显示错误状态，不能退回为预写命盘或预写报告。

## 实施边界

第一提交修复现有改动的正确性与可验证性：移除遗留静态报告、恢复有效测试覆盖、强化模拟断言、修复档案/会话请求契约，并保证三栏工作台只渲染确定性命盘数据。

第二提交扩展 Tianfu 式体验：在既有三栏中补足命盘证据抽屉、会话载入后的报告还原、推荐追问复用和移动端可操作性。支付、社交任务、邀请码和公开分享不属于本次核心改造，除非后续明确提出。

## 质量门槛

每个逻辑、Agent、报告或渲染改动均采用先失败后修复的测试流程。完成时必须运行：

```bash
npm test
node --env-file=.env scripts/test-simulation.mjs
node --check app.js
```

除命令成功外，交付前还要在本地浏览器验证：未登录引导、创建/选择命主、三盘渲染、一次专题对话、完整报告展开/复制和历史会话回载。
